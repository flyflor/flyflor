判断当前请求应当直接执行、先停在用户确认计划，还是询问缺失信息。

只返回一个 JSON 对象：
{
"decision": "direct" | "plan" | "ask",
"reason": string,
"confidence": number,
"planTitle": string,
"planSummary": string,
"askPrompt": string
}

规则：

- 只根据请求含义、显式约束、可用上下文和交互模式判断。不要依赖关键词列表、标点、请求长度或固定句式。
- 交互模式是 "{{interactionMode}}"。
- 交互模式只决定普通工作是否应先停在用户确认计划。它不覆盖冲突路由、提问规则或工具安全规则。
- 在 "plan" 交互模式下，除非缺失必要信息，否则选择 "plan"；只有无法负责任地产生计划时才选择 "ask"。
- 在 "act" 交互模式下，简单、可逆、能一次完成的任务选择 "direct"。存在多步依赖、不可逆或高风险副作用、大范围代码变更、执行前需要用户确认时选择 "plan"。
- 缺失信息会阻断直接执行或有用计划时选择 "ask"。不要编造隐藏需求。
- "confidence" 必须在 0 到 1 之间。
- decision 为 "direct" 时，planTitle、planSummary、askPrompt 留空。
- decision 为 "plan" 时，填写简短的用户可见 planTitle 和 planSummary。
- decision 为 "ask" 时，填写一个简短的用户可见问题 askPrompt。

Planning route 边界 rubric：

1. 交叉检查负责的冲突：形式数学/几何/逻辑/协议/类型定义冲突、自指或互斥硬约束、禁止表达阻塞的约束、争议分析、多视角评审、持续观察、实现加独立验证，都不是计划工作。在任何交互模式下都不要把它们转成 "plan"；上游交叉检查路由负责这条路径。
2. 计划负责的工作：只有主要阻塞是用户可见的任务拆分、排序、风险接受或执行前确认时，才选择 "plan"。计划必须是等待用户确认的草案，不是答案。
3. 提问交接负责的阻塞：缺少用户信息、范围、授权或决策，导致无法直接处理，也无法负责任地产生计划时，选择 "ask"。问题是阻塞交接，不是最终回答。
4. Direct 负责的请求：问候、普通事实/公式回答、简单解释、单次可逆请求，且约束可满足时，选择 "direct"。
5. 边界例子：严格正方形的圆面积公式或自我禁止的规则属于交叉检查；功能上线 checklist 属于计划；缺少目标环境属于提问交接；普通圆面积公式属于 direct。

如果请求描述了一组无法同时为真的精确条件，不要起草“满足它们”的计划。只有当上游路由已经处理该冲突时才返回 "direct"；只有缺少用户选择导致连有用的路由判断都无法形成时才返回 "ask"。
